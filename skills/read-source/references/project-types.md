# 项目类型精读策略

第二步必须按第一步判定的主类型选择入口。先列出对外核心能力，再把这些能力交给第三步追实现。以下策略只指导“从哪里读、读什么”，不替代源码证据。

## 工具库

典型例子：工具函数集、解析库、校验库、SDK 客户端。

### 第二步看什么

1. 从 `package.json` 的 `exports`/`main`、根 index、类型声明和 README API 列出公开导出。
2. 按使用者任务分组，而不是按文件分组。例如请求库分成创建客户端、发请求、拦截器、错误处理。
3. 标出高频核心方法与明显的扩展点，例如插件、中间件、自定义适配器。
4. 次要工具函数只作索引，不全部列入核心能力。

### 第三步怎么深入

- 从最核心的方法族选 1 到 2 条主路径，例如 `createX() -> 核心操作 -> 结果/错误`。
- 追共享内核：配置合并、管道、错误模型、公共数据结构。
- 架构应回答：公开方法如何汇聚到同一套执行内核，扩展点插在哪一层。

不要从 `utils/` 或内部 helper 文件开始读。

## UI 库

典型例子：组件库、无头组件、设计系统。

### 第二步看什么

1. 从组件文档、导出入口、`components/` 公开目录列出核心组件。
2. 区分原语组件、复合组件、布局/主题能力，不要把每个内部子组件都当成对外能力。
3. 记录代表性组件的使用方式：必要 props、组合关系、受控/非受控、插槽或 children 约定。
4. 标出跨组件的共享能力，例如主题、样式方案、无障碍行为、弹出层或焦点管理。

### 第三步怎么深入

- 选一个能代表库风格的复合组件，沿 `props -> 状态 -> 渲染/复合结构 -> 事件` 追实现。
- 再追共享基础设施：样式、主题、context、无障碍、overlay。
- 架构应回答：组件如何组合，状态放在哪一层，样式与行为如何分离。

不要按组件文件名逐个复述 JSX。

## CLI 工具

典型例子：开发命令行、运维工具、带 bin 入口的工程工具。

### 第二步看什么

1. 从 README、`--help`、bin 入口和命令框架定义列出命令树。
2. 记录主命令、子命令、全局 options 与核心 flags。
3. 标出使用者最常用的 3 到 7 个命令，而不是所有隐藏/调试命令。
4. 同时记下配置文件、插件参数或项目探测等进入命令前的输入。

### 第三步怎么深入

- 沿 `解析参数 -> 读配置/探测项目 -> 执行命令 -> 输出或写文件` 追一条主命令。
- 再看命令注册、共享 runtime、插件加载或任务编排。
- 架构应回答：命令如何注册和分发，配置与执行如何衔接，副作用发生在哪一层。

不要把每个 flag 的实现细节写成独立章节。

## 脚手架

典型例子：create-* 项目生成器、页面/组件生成器、preset 模板工具。

### 第二步看什么

1. 从 README 和 CLI/API 入口列出它能生成什么：应用、页面、组件、配置或其他产物。
2. 找出模板、generator、preset、plugin 或 snapshot 目录。
3. 记录一次生成的可见步骤：提问/参数、选择模板、渲染、写文件、安装依赖。
4. 标出可扩展点：自定义模板、插件、钩子。

### 第三步怎么深入

- 沿 `调用生成器 -> 收集参数 -> 解析模板 -> 写入产物` 追主路径。
- 看模板变量、文件映射、冲突处理和钩子执行顺序。
- 架构应回答：生成能力如何映射到模板与插件，写入过程如何保证可重复。

不要把模板文件内容当成架构本身。模板是产物证据，生成器才是实现。

## Agent 项目

典型例子：Agent runtime、带 tool/skill 的助手项目、技能仓库、多 Agent 编排。

### 第二步看什么

1. 从 README、`AGENTS.md`、`SKILL.md`、agent 配置或 tool 注册表列出对外能力。
2. 分清三类表面对象：agent 自身、它可调用的 tools、它可加载的 skills/prompts。
3. 记录一次完整对话或任务的可见循环：接收输入、选择技能或工具、执行、观察、回复。
4. 标出上下文来源：系统提示、记忆、仓库文件、MCP 或外部 API。

### 第三步怎么深入

- 沿 `用户输入 -> 组装上下文 -> 决策/选工具 -> 执行 -> 写回结果` 追主循环。
- 再看 tool 注册、skill 加载、权限/沙箱、终止条件。
- 架构应回答：循环如何运转，技能与工具如何被发现和调用，状态保存在哪里。

不要把 prompt 原文或技能文档复述成架构。先确认它们在运行时如何被加载和使用。

## 应用或框架

当主类型不属于以上五类时使用，例如 Web 应用、后端服务、开发框架、运行时。

### 第二步看什么

1. 先从 README 找出使用者主路径：启动应用、处理请求、渲染页面、执行插件或扩展框架。
2. 列出该主路径上的公开入口，例如路由、生命周期钩子、插件 API、配置项。
3. 只把支撑主路径的模块列入核心能力；后台脚本、示例和内部工具降为补充。

### 第三步怎么深入

- 沿一条端到端用户路径追实现，例如 `请求进入 -> 路由/匹配 -> 业务处理 -> 响应`。
- 再抽象分层：入口、领域逻辑、基础设施、外部集成。
- 架构应回答：控制如何穿过各层，扩展点在哪里，状态与数据如何流动。

## 混合项目

一个仓库可以同时是库和 CLI、框架和脚手架、Agent 与工具集。处理规则：

1. 主类型取使用者最主要的用法，只采用一份主策略。
2. 次要类型只补充入口，例如库项目附带的 CLI 只列入能力清单中的“命令入口”，不改写成 CLI 专题。
3. 第三步仍只追主类型的一条主路径；次要形态仅在与主路径相交时展开。

## 选择入口时的共同禁令

- 不要从测试快照、构建产物、lockfile 或第三方目录开始建立能力清单。
- 不要把内部 helper、私有组件或未导出模块当成核心能力。
- 找不到公开入口时，回到第一步补读文档和清单，不要改用“把 src 下文件列一遍”代替。
