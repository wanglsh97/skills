# Read Source 完整工作流

以用户的问题为中心阅读源码，建立足够准确的实现路径；不要为了“了解整个仓库”而无边界地遍历文件。

## 内部源码锚点（必须先完成）

开始源码学习前自动选择仓库当前最新 Git tag。不要要求、询问或等待用户指定 tag，也不要使用分支、`HEAD` 或裸 commit 代替 tag。此过程只用于内部确定本次读取的源码快照，不属于交付内容。

选择最新 tag 时：

1. 若远程仓库可访问，先刷新远程 tag 信息，但不要切换或改动用户当前 checkout。无法访问远程时，使用本地已有 tag；“最新”仅相对于实际可访问的 tag 集合。
2. 按 Git `creatordate` 从新到旧排序并选择第一项；带注释 tag 使用 tagger date，轻量 tag 使用其目标 commit 日期。日期相同则按 tag 名升序选择，确保结果可复现。
3. 立即将选中的 tag 解析为完整 commit SHA，后续只从该 commit 读取源码。

选定 tag 后：

1. 整个任务都从固定 commit 读取文件和搜索符号，不依赖当前工作区内容。优先直接读取 Git 对象，确需普通文件树时使用隔离的临时 worktree。
2. tag 名、排序日期、选择来源、选择规则和 commit SHA 都是内部控制信息。不得将它们写入阶段产物、最终 Markdown、目录名、阶段回复或最终回复，也不得通过固定 commit 链接间接暴露。
3. `temp/manifest.md` 仅可保存用于恢复和一致性检查的 `source_commit`，不得保存 tag 名、tag 日期或选择过程；`source_commit` 不得复制到其他产物，并在任务完成时随 `temp` 删除。
4. 若有证据来自外部依赖或其他源码快照，明确标注其边界，但不要披露内部 tag 信息，也不能混入当前源码结论。
5. 仓库没有任何有效 tag 时停止；只向用户说明无法建立所需的稳定源码快照，不展示 tag 相关细节，也不要回退到 branch、`HEAD` 或裸 commit，除非用户明确修改这一约束。

## 临时阶段产物（必须）

确定内部源码锚点后，先确定本次任务唯一的产物项目目录名：

1. 新任务默认使用源码仓库名作为 `<项目名>`，目标为 `.read-source/<项目名>/`。
2. 若该目录已经存在，使用任务开始当天的本地日期追加 `_YYYY-MM-DD`，例如 `.read-source/<项目名>_2026-12-12/`。
3. 若同一天的带日期目录也已存在，继续追加递增序号，例如 `<项目名>_2026-12-12_2`、`<项目名>_2026-12-12_3`，直到取得不存在的目录；不得覆盖或复用其他任务的目录。
4. 若是在恢复一个未完成任务，读取其 `manifest.md` 并继续使用已经记录的准确目录，不重新执行目录避让。

后文使用 `<产物项目目录名>` 表示最终选中的目录名，它可能是原始项目名，也可能包含日期及递增序号。在当前工作目录中建立以下临时产物目录：

```text
.read-source/
`-- <产物项目目录名>/
    `-- temp/
        |-- manifest.md
        |-- 01-overview.md
        |-- 02-capability-architecture.md
        |-- 03-book/
        |   |-- outline.md
        |   |-- chapters/
        |   `-- evidence-audit.md
        `-- 04-publication-verification.md
```

`manifest.md` 记录源码仓库名、产物项目目录名、目录选择日期及避让原因、内部 `source_commit`、临时目录绝对路径、各阶段状态及产物清单；每完成一个阶段立即更新。它是任务控制文件，不得把 `source_commit` 传播到阶段或最终产物。

创建或复用 `temp` 前先解析并检查准确路径：

- 路径必须严格位于当前工作目录的 `.read-source/<产物项目目录名>/temp/`，不能通过未解析变量、宽泛 glob 或符号链接指向其他位置。
- 现有 `manifest.md` 与当前仓库及内部 `source_commit` 一致时，从现有产物继续；不得无理由重做已完成阶段。
- 目录不存在时创建；目录已存在但内部源码锚点不一致、缺少可识别清单或包含来源不明文件时，停止并请用户处理，不能覆盖或删除。
- 每个阶段的对话回复只是摘要，完整直接结果必须落到对应 Markdown 产物。产物未写入并检查可读性时，该阶段不算完成。
- 任务暂停、中断、失败或任一校验未通过时保留整个 `temp`，并报告恢复路径。只有第四阶段全部完成后才能按清理规则删除。

## 阶段纪律

内部源码锚点确认后，严格按已定义阶段及阶段内编号顺序学习：

- 不得跳过、合并、调换或并行执行阶段，也不得因用户的问题看似具体就直接进入实现细节。
- 当前阶段的必读范围、产出和完成条件全部满足后，才能进入下一阶段。
- 每完成一个阶段，先把独立阶段记录写入约定的 `temp` 产物，明确事实、推断、未知项和证据；自动检查文件、必备内容和阶段门禁。检查通过后更新 `manifest.md`、给出简短进度与产物路径，并立即进入下一阶段，不询问、不等待用户确认。
- 阶段检查失败时留在当前阶段自动修正并重新检查，不得带着缺失项进入下一阶段。只有缺少访问权限、无法建立稳定源码快照、存在不允许覆盖的未知文件等无法安全自行解决的真实阻塞，才停止并保留 `temp`。
- 当前定义第一至第四阶段。前一阶段未完成时不得进入后一阶段；第四阶段完成后不得自行进入尚未定义的阶段。

## 第一阶段：宏观俯瞰

目标是回答“这个项目是什么、解决什么问题、适用于哪些场景”，形成后续源码学习的项目地图。严格执行以下顺序：

### 1. 读文档

阅读内部固定源码快照中的 README、项目文档和官方架构说明。提取并记录：

- 项目要解决的核心痛点，以及目标用户为何需要它；
- 项目能力边界、主要适用场景与明确不适用的场景；
- 项目自创或赋予特殊含义的核心术语，形成简短术语表；
- 文档暂未回答、需要后续阶段验证的问题。

本步骤只建立官方叙事，不进入具体源码验证。文档没有说明的内容标为未知，不自行补全。

### 2. 看技术栈

检查仓库实际存在的依赖与构建清单，例如 `package.json`、`go.mod`、`Cargo.toml`、`requirements.txt`、工作区清单及锁文件。识别：

- 主要语言、运行时、框架和关键库；
- 构建、测试、打包及包管理方式；
- 单仓、多包或多语言工作区形态；
- 从技术栈推断的学习重点和成本。

依赖文件能直接确认的内容记为事实；对架构和学习成本的判断必须标为推断。不要在本步骤追入依赖源码或业务实现。

### 3. 看目录结构

只查看一级和二级目录，不展开更深层级，也不阅读业务实现文件。排除 `.git`、构建产物、依赖缓存等噪声目录。完成以下工作：

- 为主要目录推测职责，并为每项推测标注依据与置信度；
- 判断项目可能采用的架构模式，例如 MVC、DDD 分层或 Clean Architecture，但不得把目录命名直接当作定论；
- 若官方文档包含架构图或模块说明，逐项对照验证目录职责，并记录一致之处与冲突之处；
- 若没有官方架构资料，明确写明“未找到官方架构图或说明”。

### 第一阶段完成条件

将阶段记录写入 `temp/01-overview.md`。产物必须包含：项目一句话定位、核心痛点、适用场景、核心术语表、技术栈概览、学习成本预估、两层目录地图、架构假设、文档与目录的验证结果，以及留给后续阶段的问题清单；不得包含 tag、commit SHA 或版本锚点描述。文件缺失或缺少任何一项时，第一阶段尚未完成。

## 第二阶段：能力架构

目标是在第一阶段项目地图的基础上大致熟悉代码，并用图示说明“这套代码提供哪些能力，以及这些能力在运行时如何协作”。这里的架构是**代码的能力架构**，不是仓库目录、包或文件之间的组织结构。

开始前先读取第一阶段记录，并通过 `manifest.md` 在内部确认其属于当前 `source_commit`。记录缺失、不完整或内部源码锚点不一致时，返回第一阶段，不得继续。不得把该检查信息写入阶段产物。随后严格执行以下顺序：

### 1. 确定能力边界

结合第一阶段的核心痛点、术语和问题清单，从公开 API、命令入口、示例、文档及关键测试中识别代码对使用者提供的主要能力。形成能力清单，并说明每项能力的输入、输出、触发方式和价值。

不要把目录名、包名或内部类名直接当作能力。能力应从使用者或运行时视角描述，例如“调度更新”“协调渲染”“持久化任务状态”，而不是“`src` 层”“utils 包”或某个文件名。

### 2. 大致熟悉实现

围绕能力清单阅读必要的公开入口、导出接口、核心类型、中央协调逻辑和代表性测试。使用精确搜索追踪定义、引用、注册和一到两条代表性主路径，但不在本阶段穷举所有分支或逐行钻研实现细节。

为每项能力确认：

- 哪些运行时角色或子系统共同完成它；
- 控制如何进入、转移并结束；
- 关键数据如何产生、转换和传递；
- 是否存在调度、缓存、并发、事件、插件或宿主环境等协作边界；
- 是否存在明确的状态、生命周期及状态转换条件。

### 3. 抽象能力架构

从已验证的主路径中抽象能力组件及其关系。组件按运行时职责命名，不按仓库目录命名；目录和文件只作为证据索引。明确区分对外能力、核心机制、基础支撑与外部边界，并标出控制流、数据流、事件流或依赖方向。

例如，分析 React 时，应总结组件模型、更新调度、协调、提交、宿主渲染与事件触发更新等能力如何协作，而不是把 `packages/react`、`packages/react-dom`、`packages/scheduler` 画成仓库结构图。

### 4. 绘制图示

使用 Mermaid 绘制图示，并按实际代码语义选择图型：

- 必须提供一张总体能力架构流程图，展示主要能力组件、边界及核心控制或数据方向；
- 对最具代表性的端到端场景绘制时序图，展示参与者、调用先后和关键返回；
- 只有代码存在有意义的生命周期或状态转换时才绘制状态图，并标注触发条件；没有真实状态机时明确说明，不得为了齐全而虚构；
- 必要时补充数据流图、事件流图或子流程图，但每张图只回答一个清晰问题。

每个重要节点和连线必须能追溯到当前源码快照中的证据。图后附简短证据索引，将能力组件或关键交互映射到具体符号与文件。无法确认的关系使用“推断”标记，不能画成已证实事实。

### 第二阶段完成条件

将阶段记录写入 `temp/02-capability-architecture.md`。产物必须包含：第一阶段结论的承接说明、能力边界、能力清单、运行时角色及职责、核心控制流与数据流、总体能力架构流程图、至少一个代表性场景的时序图、适用时的状态图、图示证据索引，以及尚未验证的问题清单。文件缺失或图只是目录、包依赖关系时，第二阶段不算完成。

## 第三阶段：章节化精读

目标是把前两阶段形成的项目地图和能力架构组织成一条由浅入深、前后相承的学习路径，再沿这条路径逐章精读源码。书稿不是源码知识百科，也不是把能力、术语、文件或机制各写一章后平铺展示；前一章必须为后一章提供理解所需的概念、问题和心智模型，读者应能随着章节推进逐步建立完整的代码能力架构。

开始前读取第一、第二阶段的完整记录，通过 `manifest.md` 在内部确认二者属于同一 `source_commit`，并确认第二阶段的能力清单、能力架构图和证据索引已经完成。任一条件不满足时返回对应阶段，不得继续；内部源码锚点不得出现在书稿内容中。

### 精读证据纪律（强制）

第三阶段的正文必须由当前固定源码快照直接支撑，严禁凭经验、惯例、命名或印象猜测和补全：

- 函数名、类型名、目录名、注释、文档和搜索命中只能作为定位线索，不能代替实现证据。必须阅读完整定义、关键调用方及必要上下文；重要行为再用测试或另一条调用路径交叉验证。
- 前两阶段标为“推断”的内容进入第三阶段后只是假设，必须重新用源码验证。验证前不得写进正文、图示或章节总结。
- 关于控制流、数据流、状态转换、边界条件、不变量和错误处理的每个关键结论，都必须能追溯到具体符号与源码位置。图中的节点和连线遵守同一规则。
- 不得因为某项目使用常见框架或设计模式，就假设它遵循该框架的典型实现。只描述实际读取的源码所执行的行为。
- 源码能证明“如何工作”，未必能证明“作者为什么这样设计”。只有源码注释、项目文档或用户明确要求查阅的版本历史给出直接依据时，才陈述设计动机；否则写成可观察的作用，或标为“尚未确认”。
- 遇到动态注入、生成代码、平台行为或外部依赖且当前仓库没有实现证据时，停在可验证边界，明确列为未知，不推测边界之外的行为。
- 多处证据冲突时展示冲突及各自位置，不自行选择一个看似合理的解释。

证据不足的内容统一放入“尚未确认的问题”，不能用“大概”“通常”“应该”“可能是”等措辞包装后混入书稿正文。

### 关键源码呈现规范（强制）

书稿必须让读者看到支撑关键逻辑的源码，但只保留理解该知识点所需的最小内容：

- 保留原始类名、方法名、函数名、类型名和关键字段名，使读者能回到仓库准确搜索；不得为了易读而擅自改名。
- 对关键入口、核心分支、状态更新、重要调用和返回路径，可给出“源码节选（有删减）”。节选保留原始语言和语句，只删除与当前知识点无关的样板、日志、重复分支或辅助细节，并用明确的省略标记表示删减。
- 不复制整份文件、整类或与知识点无关的大段方法。若完整方法很长，只展示方法签名以及证明当前逻辑所需的条件、调用和状态变化。
- 需要进一步压缩时，另给出“逻辑缩减（非原始源码）”或伪代码。缩减版必须保留原始符号名、判断条件、执行顺序、关键副作用和返回/错误语义，不能合并会改变行为的分支，也不能补入源码不存在的步骤。
- 原始节选与逻辑缩减必须使用不同标题，不能让读者误以为缩减版是可直接编译的原始源码。来自不同文件的片段分别展示并分别标注来源，不能拼接成一段伪装为连续源码。
- 每段节选或缩减版紧邻标注仓库相对路径、原始符号和行号；正文解释必须与该片段及完整源码上下文一致。

源码片段用于证明和辅助理解，正文负责解释逻辑。不得用大量源码堆砌代替章节叙述。

### 1. 设计全书目录

先把第二阶段的能力架构转换为认知依赖图：识别理解每项机制之前必须掌握的概念、数据模型、运行时角色和前置流程，再选择一条能串联主要能力的代表性端到端场景作为学习主线。按认知依赖而不是按源码位置进行拓扑排序；并行能力先讲共同基础，再分别展开，最后在能够比较或汇合的位置重新合流。

学习路径通常从“项目解决的问题与最小使用模型”进入，随后建立核心抽象和关键数据模型，再跟随一条完整执行链理解主机制，最后扩展到重要分支、状态与生命周期、调度或并发、错误处理、优化、扩展边界和典型场景。这个顺序不是固定模板，应根据实际代码删减、合并或调整；唯一不变的标准是读者不需要依赖尚未解释的后续概念来理解当前章节。

为每个章节先定义：

- 章节名称及其代表的大能力模块；
- 读者进入本章前已经掌握的内容；
- 本章承接上一章的哪个问题，以及要回答的核心问题；
- 本章只新增哪些概念和关系，读者学完后应形成怎样的新心智模型；
- 本章为何必须出现在当前位置，它为后续哪一章提供前置知识；
- 章节结尾用于自然引出下一章的未决问题或执行步骤；
- 计划包含的小节及每个小节负责解释的具体内容；
- 预计精读的入口、核心符号、测试和源码范围。

章节标题按读者要建立的能力或机制模型命名，不能简单照搬一级目录、包名、文件名或术语名。建立两张矩阵：一张“前置心智模型 → 当前章节新增模型 → 后续解锁内容”的学习路径矩阵，一张“第二阶段能力 → 章节/小节”的能力覆盖矩阵。前者保证由浅入深，后者保证能力不遗漏；不能用覆盖完整替代学习顺序合理。跨章节概念设置唯一主讲位置，首次使用前必须已经解释，其他章节只做必要回顾和交叉引用。

将学习主线说明、章节认知依赖图、完整目录、逐章承接说明、学习路径矩阵和能力覆盖矩阵写入 `temp/03-book/outline.md`。自动检查：

- 目录能否从一个最小心智模型连续推导到完整能力架构；
- 每章的前置概念是否已经在前文建立，是否存在依赖后文才能理解的倒置；
- 相邻章节之间是否有明确的“承接问题 → 新增模型 → 下一步问题”；
- 章节若被任意换序是否仍毫无影响；若是，说明目录仍是平铺知识点，必须重构；
- 是否为了对应目录、包、类或术语而创建了孤立章节；这类内容必须并入其实际参与的执行路径；
- 两张矩阵是否同时覆盖学习依赖和代码能力，且没有重复主讲或遗漏。

检查通过后直接开始章节源码精读，不等待用户确认；检查未通过时先修订目录、依赖图和两张矩阵。

### 2. 逐章制定小节

目录自动检查通过后，一次只处理一个章节，并严格按照学习路径顺序推进。开始某章前，根据该章承接的问题和本章新增心智模型细化小节。小节也按认知递进组织：先回收前文已知条件并提出当前问题，再引入解决问题所需的最少新抽象，随后沿控制流或数据流展开实现，最后用分支、状态、错误路径或测试补全边界并引出下一节。只选择该模块实际存在且有助于当前理解的内容，不机械套用固定模板。

一个小节只解决一个明确问题，但不能写成脱离上下文的知识卡片。若内容大到包含多个认知步骤，应按依赖拆分；若只是单个文件、类、术语或 API 的独立说明，应重新放回它参与的执行路径，解释它为何在此出现以及改变了读者的哪部分心智模型。

### 3. 按小节精读源码

围绕当前小节从入口追踪到核心实现和出口，阅读完整的相关函数、类型及必要上下文，并用定义、调用方、测试、配置和错误路径交叉验证。精读时重点回答：

- 这段机制在源码中实际承担什么作用，解决本章能力中的什么可验证问题；
- 输入、输出、核心不变量和关键数据结构是什么；
- 控制流与数据流如何穿过相关组件；
- 正常路径、关键分支、边界条件和失败路径如何处理；
- 它与前置小节、其他章节及第二阶段能力架构如何衔接。

不得为写后续小节而跳过当前小节的未决问题。确实需要后续机制才能解释时，明确建立交叉引用并限定当前结论，不提前展开后续章节。

### 4. 整理为书稿内容

每个章节使用连贯的教学叙事，而不是源码检索日志或知识点合集。章节至少包含：与上一章的衔接、当前问题与学习目标、已具备的前置心智模型、按认知递进组织的小节、必要的 Mermaid 图、关键源码证据、更新后的心智模型、通往下一章的问题，以及尚未解决的问题。

每个小节从前文已知内容出发提出一个自然出现的问题，再解释源码能够确认的新概念与实现，最后按“关键源码呈现规范”给出最小源码节选或逻辑缩减及精确证据，并说明它如何更新当前心智模型。图示必须服务于当前认知步骤，并与经过源码验证的能力架构保持一致；不要一次把尚未讲解的完整架构全部摊给读者。

### 5. 章节门禁

完成当前章节后，逐项审计关键结论和图示关系是否都有具体源码证据，检查该章所有小节是否都有明确问题、实现解释和源码位置，并核对其与能力架构图、前置章节及两张矩阵是否一致。额外确认本章没有提前使用未解释概念，开头能承接上一章，结尾形成了足以进入下一章的新心智模型和明确问题。发现无证据结论时删除或移入“尚未确认的问题”；发现认知跳跃时补齐前置解释或调整目录，不能用交叉引用掩盖关键知识缺口。先输出或写入完整章节内容，再标记该章完成；未通过检查时不得进入下一章。

若精读证据推翻了第二阶段的推断，应明确记录修正原因并更新能力架构及后续章节计划，不能悄悄改写旧结论。修正不允许跳过当前章节；确需调整目录时，自动更新 `outline.md`、章节认知依赖图、学习路径矩阵和能力覆盖矩阵，记录变更理由并重新执行目录检查，然后继续，不等待用户确认。

### 第三阶段完成条件

将自动检查通过的学习路径和目录写入 `temp/03-book/outline.md`，逐章书稿写入 `temp/03-book/chapters/`，证据审计、学习路径审计与架构修正记录写入 `temp/03-book/evidence-audit.md`。这些产物必须包含：学习主线、章节认知依赖图、检查通过的全书目录、逐章承接说明、学习路径矩阵、能力覆盖矩阵、按顺序完成的全部章节及小节、跨章节术语与源码索引、对第二阶段能力架构的验证或修正记录、章节证据审计结果，以及全书遗留问题清单。任一规定文件缺失，章节之间没有可验证的认知递进，目录可任意换序而不影响理解，任一大能力只有章节标题而没有小节内容，正文退化为文件说明或知识卡片合集，或存在无法追溯到源码的关键结论时，第三阶段不算完成。

## 第四阶段：Markdown 落盘与逐章复核

目标是在第三阶段完整书稿的基础上生成标准 Markdown 产物，再按照 Markdown 章节逐章回到内部固定源码快照核对逻辑，确保文档中的每个关键知识点都对应到具体源码。

开始前确认第三阶段已达到全部完成条件，并通过 `manifest.md` 在内部校验仍使用同一 `source_commit`。任务执行期间不重新选择源码快照，不得混用其他版本，也不得在产物或回复中展示该内部检查。

### 1. 建立最终产物目录

产物根目录固定为当前工作目录下的 `.read-source/`。阶段直接结果先保存在项目 `temp` 中，最终书稿直接写入产物项目目录，不使用 tag 或 commit 信息作为目录层级：

```text
.read-source/
`-- <产物项目目录名>/
    |-- temp/
    |   `-- ...阶段产物
    |-- README.md
    |-- chapters/
    |   |-- 01-<章节名>.md
    |   `-- 02-<章节名>.md
    |-- source-index.md
    `-- verification.md
```

基础项目名取源码仓库根目录名；若目录名不能唯一识别仓库，则使用远程仓库名并记录来源。按照前述避让规则得到产物项目目录名。目录名不得包含 tag、commit SHA 或其他版本锚点信息。

写入最终文件前检查目标。新任务已经通过产物项目目录避让保证目录唯一；若仍发现无法识别的同名文件，先报告冲突并请求用户确认，不得直接覆盖。第四阶段的逐章核对过程同步写入 `temp/04-publication-verification.md`，最终内容再归入项目目录的 `verification.md`。

### 2. 生成标准 Markdown 书稿

`README.md` 作为全书入口，包含仓库标识、项目简介、学习主线、推荐阅读顺序、每章为何位于当前位置的简短说明和目录，不包含 tag、commit SHA、版本校验或源码锚点描述。目录必须呈现由浅入深的阅读路径，不能只罗列章节链接。`chapters/` 中每个经确认章节对应一个 Markdown 文件，小节保留第三阶段确定的稳定编号。`source-index.md` 汇总知识点与源码证据，`verification.md` 记录逐章核对结果和修订。

所有文件使用 UTF-8、标准 Markdown 标题、列表、表格、带语言标识的代码围栏和标准相对链接。每个章节文件只使用一个一级标题；Mermaid 图使用 `mermaid` 围栏。不要依赖只在特定编辑器中生效的私有指令。

每个章节直接进入章节内容，不展示 tag、commit SHA 或版本信息。源码引用必须包含仓库相对路径、符号名和精确行号，并使用文本引用；不要生成包含 commit 或 tag 的远程链接，也不要链接到可能变化的当前分支。

### 3. 建立关键知识点证据索引

为每章的关键知识点分配稳定编号。关键知识点包括公开契约、核心数据结构与不变量、控制流、数据流、状态转换、重要分支、错误处理和扩展边界。

在正文相关段落附近标注知识点编号和源码引用，并在 `source-index.md` 中记录：知识点编号、简明结论、所属章节与小节、源码路径、符号、行号、正文中的源码呈现方式、交叉验证证据和核对状态。一个知识点涉及多个组件时列出完整证据链，不能只引用入口文件。

### 4. 按 Markdown 章节逐章核对

严格按照 `README.md` 目录顺序，一次只核对一个章节。核对时重新读取内部固定源码快照，不把第三阶段笔记本身当作证据。逐项检查：

- 每个关键知识点是否与实际定义、调用路径和测试一致；
- 描述的控制流、数据流、状态变化、分支条件和错误路径是否完整准确；
- 代码片段、符号名、路径和行号是否对应内部固定源码快照；
- 源码节选是否保持原始语句，逻辑缩减是否保持原始符号、条件、顺序、副作用及返回/错误语义；
- 每个关键逻辑是否展示了足够理解的最小源码，而没有复制无关的大段实现；
- Mermaid 图中的重要节点和连线是否都有源码支撑；
- 章节之间的术语、前置关系和交叉引用是否一致。

核对结果只能是“已验证”“已修正”或“未获源码支持”。发现错误时，以源码为准修正文档、图示和证据索引，再重新核对该知识点；未获支持的内容从正文和图示中删除并移入遗留问题。当前章节仍有未核对的关键知识点时，不得进入下一章。

在 `verification.md` 中按章节记录核对范围、证据、发现的问题、修改内容和最终状态。不能只写笼统的“已检查”。

### 5. 全书一致性审计

所有章节核对完成后，检查目录链接、章节编号、标题层级、代码围栏、Mermaid 围栏、术语、交叉引用、知识点编号和源码索引是否一致。逐章复演学习路径，确认概念首次出现前已有足够前置知识、每章确实更新了读者心智模型、相邻章节衔接自然、README 的阅读顺序与正文一致，且没有退化为平铺知识点。除 `temp/manifest.md` 的内部 `source_commit` 控制字段外，确认所有阶段直接产物与最终 Markdown 都不含 tag 名、tag 日期、选择过程、commit SHA、版本锚点描述或暴露这些信息的链接，并且没有指向当前分支或未经验证源码的结论。

最终在 `verification.md` 汇总已验证、已修正和被移除的知识点数量，并记录仓库、核对完成状态及仍存在的源码边界；不得记录 tag、commit SHA 或版本锚点信息。任何正文关键知识点缺少源码对应关系时，第四阶段不得完成。

最终产物目录完整通过检查后，确认 `temp/04-publication-verification.md` 的必要记录已经进入最终 `verification.md`，且其他阶段产物所承载的内容已进入最终书稿。随后只删除本次任务创建并由 `manifest.md` 确认的 `.read-source/<产物项目目录名>/temp/` 精确目录：

- 删除前再次解析绝对路径，确认父目录正是当前工作目录下的 `.read-source/<产物项目目录名>/`，目标名正是 `temp`，且目标不是符号链接。
- 不使用宽泛路径、glob、未解析变量或仓库根目录执行递归删除；不删除同目录下的最终 Markdown 产物。
- 删除后确认 `temp` 不再存在，并确认最终目录仍完整可读。
- 只要最终校验未通过、复制不完整或任务尚未完成，就保留 `temp`，不得提前清理。

### 第四阶段完成条件

最终目录及规定的 Markdown 文件全部存在；README 明确展示学习主线和推荐顺序；章节按认知依赖由浅入深且每章均通过逐章核对；正文、代码片段、逻辑缩减和图示中的关键知识点都能在 `source-index.md` 找到对应源码；关键逻辑包含最小且可识别的源码呈现；`verification.md` 留有具体核对记录、学习路径审计和全书汇总；所有交付文件均不包含 tag、commit SHA 或版本锚点描述；正文不包含“未获源码支持”的结论，也没有无必要的大段源码复制；最终目录复核后，`temp` 已按精确路径安全删除且最终目录仍可读。缺少任一条件时，不得宣布产物完成。

## 控制范围

- 第一阶段只做宏观认知，即使发现明显入口，也只把它记入后续问题清单，不继续追踪。
- 第二阶段只形成有源码证据的能力级模型，不穷举所有实现分支，也不把推断包装成事实。
- 第三阶段严格按确认后的目录逐章逐节精读；未完成当前章节时，不得切换到下一章。
- 第四阶段只把第三阶段已经完成的书稿落盘并按章复核，不能借落盘之名添加未经精读的新结论。
- 四个阶段只在 `.read-source/<产物项目目录名>/temp/` 写入直接阶段产物；最终完成后仅删除经 `manifest.md` 确认的该 `temp`，不得扩大清理范围。
- 遇到生成代码、第三方依赖或运行时注入时，标明边界，不假装已看到外部实现。
- 只有当用户询问“为什么这样写”或历史原因时，才使用 Git 历史或 blame；不要用历史替代当前实现证据。
- 用户只要求阅读、解释或诊断时，不修改源码仓库。第四阶段仅可在当前工作目录的 `.read-source/` 中创建或更新约定的 Markdown 产物；若同时要求实现源码变更，先完成必要的源码理解，再在既定范围内修改。

## 输出要求

直接给出当前阶段摘要和产物路径，不展示内部源码锚点。引用实际读取的真实文件及尽可能精确的行号；本地链接不得携带或展示 tag、commit SHA 等版本信息。清楚区分：

- 当前阶段证据可直接确认的事实；
- 根据多处证据得出的推断；
- 因缺少运行时状态、外部依赖或配置而仍不确定的部分。

避免逐文件复述、粘贴大段内容或只列名称。解释每项关键证据为何相关，以及它在当前阶段认知模型中的作用。

第三阶段的输出使用稳定的“章 → 节 → 小节内容”层级，保持术语、编号和交叉引用一致，使各章合起来能够作为连续阅读的源码书稿。

第三阶段正文只容纳源码已验证的内容。仍需验证的假设只能进入独立的“尚未确认的问题”区，不得参与正文推导或图示建模。

第四阶段完成时，最终回复必须给出最终产物目录、仓库、章节核对状态、遗留边界和 `temp` 清理结果；不得展示 tag、commit SHA、版本锚点或选择过程，也不能只说“文档已生成”。
