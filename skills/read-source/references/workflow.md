# Read Source 完整工作流

以用户的问题为中心阅读源码，建立足够准确的实现路径；不要为了“了解整个仓库”而无边界地遍历文件。

## 版本锚点（必须先完成）

开始源码学习前，必须获得用户明确指定的 Git tag。若请求中没有 tag，先列出可用 tag 作为参考并请用户指定；在用户选定前，不得开始深入阅读或记录源码结论。不要自行默认分支、`HEAD`、最新 tag 或自行推测版本。

收到 tag 后：

1. 验证该 tag 存在，并将其解析为完整 commit SHA。tag 名用于表达版本语义，commit SHA 用于防止 tag 后续被移动。
2. 整个任务都从该 commit SHA 读取文件和搜索符号，不依赖当前工作区内容。不要切换或改动用户当前 checkout；优先直接读取 Git 对象，确需普通文件树时使用隔离的临时 worktree。
3. 所有学习记录和最终回答开头都写明仓库、tag 与完整 commit SHA。若有一部分证据来自其他版本或外部依赖，单独标注其版本，不能混入当前 tag 的结论。
4. 如果 tag 不存在、无法解析或目标仓库没有 tag，停止源码学习并请用户提供有效 tag；不要用 branch 或裸 commit 替代，除非用户明确修改这一约束。

## 阶段纪律

版本锚点确认后，严格按已定义阶段及阶段内编号顺序学习：

- 不得跳过、合并、调换或并行执行阶段，也不得因用户的问题看似具体就直接进入实现细节。
- 当前阶段的必读范围、产出和完成条件全部满足后，才能进入下一阶段。
- 每完成一个阶段，先输出独立的阶段记录，明确事实、推断、未知项和证据，再停止等待下一阶段。
- 当前定义第一至第四阶段。前一阶段未完成时不得进入后一阶段；第四阶段完成后不得自行进入尚未定义的阶段。

## 第一阶段：宏观俯瞰

目标是回答“这个项目是什么、解决什么问题、适用于哪些场景”，形成后续源码学习的项目地图。严格执行以下顺序：

### 1. 读文档

阅读固定 commit 中的 README、项目文档和官方架构说明。提取并记录：

- 项目要解决的核心痛点，以及目标用户为何需要它；
- 项目能力边界、主要适用场景与明确不适用的场景；
- 项目自创或赋予特殊含义的核心术语，形成简短术语表；
- 文档暂未回答、需要后续阶段验证的问题。

本步骤只建立官方叙事，不进入具体源码验证。文档没有说明的内容标为未知，不自行补全。

### 2. 看技术栈

检查仓库实际存在的依赖与构建清单，例如 `package.json`、`go.mod`、`Cargo.toml`、`requirements.txt`、工作区清单及锁文件。识别：

- 主要语言、运行时、框架和关键库；
- 构建、测试、打包及包管理方式；
- 单仓、多包或多语言工作区形态；
- 从技术栈推断的学习重点和成本。

依赖文件能直接确认的内容记为事实；对架构和学习成本的判断必须标为推断。不要在本步骤追入依赖源码或业务实现。

### 3. 看目录结构

只查看一级和二级目录，不展开更深层级，也不阅读业务实现文件。排除 `.git`、构建产物、依赖缓存等噪声目录。完成以下工作：

- 为主要目录推测职责，并为每项推测标注依据与置信度；
- 判断项目可能采用的架构模式，例如 MVC、DDD 分层或 Clean Architecture，但不得把目录命名直接当作定论；
- 若官方文档包含架构图或模块说明，逐项对照验证目录职责，并记录一致之处与冲突之处；
- 若没有官方架构资料，明确写明“未找到官方架构图或说明”。

### 第一阶段完成条件

阶段记录必须包含：版本锚点、项目一句话定位、核心痛点、适用场景、核心术语表、技术栈概览、学习成本预估、两层目录地图、架构假设、文档与目录的验证结果，以及留给后续阶段的问题清单。缺少任何一项时，第一阶段尚未完成。

## 第二阶段：能力架构

目标是在第一阶段项目地图的基础上大致熟悉代码，并用图示说明“这套代码提供哪些能力，以及这些能力在运行时如何协作”。这里的架构是**代码的能力架构**，不是仓库目录、包或文件之间的组织结构。

开始前先读取第一阶段记录并确认其 tag 与 commit SHA 和当前版本锚点完全一致。记录缺失、不完整或版本不一致时，返回第一阶段，不得继续。随后严格执行以下顺序：

### 1. 确定能力边界

结合第一阶段的核心痛点、术语和问题清单，从公开 API、命令入口、示例、文档及关键测试中识别代码对使用者提供的主要能力。形成能力清单，并说明每项能力的输入、输出、触发方式和价值。

不要把目录名、包名或内部类名直接当作能力。能力应从使用者或运行时视角描述，例如“调度更新”“协调渲染”“持久化任务状态”，而不是“`src` 层”“utils 包”或某个文件名。

### 2. 大致熟悉实现

围绕能力清单阅读必要的公开入口、导出接口、核心类型、中央协调逻辑和代表性测试。使用精确搜索追踪定义、引用、注册和一到两条代表性主路径，但不在本阶段穷举所有分支或逐行钻研实现细节。

为每项能力确认：

- 哪些运行时角色或子系统共同完成它；
- 控制如何进入、转移并结束；
- 关键数据如何产生、转换和传递；
- 是否存在调度、缓存、并发、事件、插件或宿主环境等协作边界；
- 是否存在明确的状态、生命周期及状态转换条件。

### 3. 抽象能力架构

从已验证的主路径中抽象能力组件及其关系。组件按运行时职责命名，不按仓库目录命名；目录和文件只作为证据索引。明确区分对外能力、核心机制、基础支撑与外部边界，并标出控制流、数据流、事件流或依赖方向。

例如，分析 React 时，应总结组件模型、更新调度、协调、提交、宿主渲染与事件触发更新等能力如何协作，而不是把 `packages/react`、`packages/react-dom`、`packages/scheduler` 画成仓库结构图。

### 4. 绘制图示

使用 Mermaid 绘制图示，并按实际代码语义选择图型：

- 必须提供一张总体能力架构流程图，展示主要能力组件、边界及核心控制或数据方向；
- 对最具代表性的端到端场景绘制时序图，展示参与者、调用先后和关键返回；
- 只有代码存在有意义的生命周期或状态转换时才绘制状态图，并标注触发条件；没有真实状态机时明确说明，不得为了齐全而虚构；
- 必要时补充数据流图、事件流图或子流程图，但每张图只回答一个清晰问题。

每个重要节点和连线必须能追溯到该 commit 中的源码证据。图后附简短证据索引，将能力组件或关键交互映射到具体符号与文件。无法确认的关系使用“推断”标记，不能画成已证实事实。

### 第二阶段完成条件

阶段记录必须包含：第一阶段结论的承接说明、能力边界、能力清单、运行时角色及职责、核心控制流与数据流、总体能力架构流程图、至少一个代表性场景的时序图、适用时的状态图、图示证据索引，以及尚未验证的问题清单。图若只是目录或包依赖关系，第二阶段不算完成。

## 第三阶段：章节化精读

目标是把前两阶段形成的项目地图和能力架构组织成一本循序渐进的源码书稿：先按大的能力模块划分章节，再按章节逐一精读源码并整理内容。章节不是文件清单；一个章节承载一个大的能力模块，具体概念、机制、流程和实现必须放入该章的小节。

开始前读取第一、第二阶段的完整记录，确认二者与当前版本锚点使用相同的 tag 和 commit SHA，且第二阶段的能力清单、能力架构图和证据索引已经完成。任一条件不满足时返回对应阶段，不得继续。

### 精读证据纪律（强制）

第三阶段的正文必须由当前 commit 的源码直接支撑，严禁凭经验、惯例、命名或印象猜测和补全：

- 函数名、类型名、目录名、注释、文档和搜索命中只能作为定位线索，不能代替实现证据。必须阅读完整定义、关键调用方及必要上下文；重要行为再用测试或另一条调用路径交叉验证。
- 前两阶段标为“推断”的内容进入第三阶段后只是假设，必须重新用源码验证。验证前不得写进正文、图示或章节总结。
- 关于控制流、数据流、状态转换、边界条件、不变量和错误处理的每个关键结论，都必须能追溯到具体符号与源码位置。图中的节点和连线遵守同一规则。
- 不得因为某项目使用常见框架或设计模式，就假设它遵循该框架的典型实现。只描述这个 tag 的代码实际执行的行为。
- 源码能证明“如何工作”，未必能证明“作者为什么这样设计”。只有源码注释、项目文档或用户明确要求查阅的版本历史给出直接依据时，才陈述设计动机；否则写成可观察的作用，或标为“尚未确认”。
- 遇到动态注入、生成代码、平台行为或外部依赖且当前仓库没有实现证据时，停在可验证边界，明确列为未知，不推测边界之外的行为。
- 多处证据冲突时展示冲突及各自位置，不自行选择一个看似合理的解释。

证据不足的内容统一放入“尚未确认的问题”，不能用“大概”“通常”“应该”“可能是”等措辞包装后混入书稿正文。

### 关键源码呈现规范（强制）

书稿必须让读者看到支撑关键逻辑的源码，但只保留理解该知识点所需的最小内容：

- 保留原始类名、方法名、函数名、类型名和关键字段名，使读者能回到仓库准确搜索；不得为了易读而擅自改名。
- 对关键入口、核心分支、状态更新、重要调用和返回路径，可给出“源码节选（有删减）”。节选保留原始语言和语句，只删除与当前知识点无关的样板、日志、重复分支或辅助细节，并用明确的省略标记表示删减。
- 不复制整份文件、整类或与知识点无关的大段方法。若完整方法很长，只展示方法签名以及证明当前逻辑所需的条件、调用和状态变化。
- 需要进一步压缩时，另给出“逻辑缩减（非原始源码）”或伪代码。缩减版必须保留原始符号名、判断条件、执行顺序、关键副作用和返回/错误语义，不能合并会改变行为的分支，也不能补入源码不存在的步骤。
- 原始节选与逻辑缩减必须使用不同标题，不能让读者误以为缩减版是可直接编译的原始源码。来自不同文件的片段分别展示并分别标注来源，不能拼接成一段伪装为连续源码。
- 每段节选或缩减版紧邻标注仓库相对路径、原始符号和行号；正文解释必须与该片段及完整源码上下文一致。

源码片段用于证明和辅助理解，正文负责解释逻辑。不得用大量源码堆砌代替章节叙述。

### 1. 设计全书目录

以第二阶段的能力架构为依据划分章节，并按认知依赖安排阅读顺序。通常先介绍基础模型和核心抽象，再进入主执行机制、支撑能力、扩展边界与典型场景；实际顺序以项目能力之间的依赖关系为准。

为每个章节先定义：

- 章节名称及其代表的大能力模块；
- 本章要回答的核心问题和读者学完后应建立的心智模型；
- 依赖的前置章节以及与后续章节的关系；
- 计划包含的小节及每个小节负责解释的具体内容；
- 预计精读的入口、核心符号、测试和源码范围。

章节标题按能力或机制命名，不能简单照搬一级目录、包名或文件名。建立“第二阶段能力 → 章节/小节”的覆盖矩阵，确保每项核心能力都有归属，避免重复讲解或遗漏。跨章节概念应设置唯一主讲位置，其他章节通过交叉引用承接。

先输出完整目录、章节说明和覆盖矩阵，等待用户确认。目录确认前不得开始章节源码精读；用户调整目录后，先更新覆盖矩阵再继续。

### 2. 逐章制定小节

目录确认后，一次只处理一个章节，并严格按照目录顺序推进。开始某章前，根据该章核心问题细化小节。小节按概念和实现逻辑组织，例如公开契约、核心抽象、关键数据结构、主执行流程、重要分支、状态与生命周期、并发或调度、错误处理、扩展机制及代表性测试；只选择该模块实际存在且有助于理解的内容，不机械套用固定模板。

一个小节只解决一个明确问题。若内容大到包含多个独立机制，应拆分小节；若只是单个文件的逐行说明，应重新抽象其在本章能力中的作用。

### 3. 按小节精读源码

围绕当前小节从入口追踪到核心实现和出口，阅读完整的相关函数、类型及必要上下文，并用定义、调用方、测试、配置和错误路径交叉验证。精读时重点回答：

- 这段机制在源码中实际承担什么作用，解决本章能力中的什么可验证问题；
- 输入、输出、核心不变量和关键数据结构是什么；
- 控制流与数据流如何穿过相关组件；
- 正常路径、关键分支、边界条件和失败路径如何处理；
- 它与前置小节、其他章节及第二阶段能力架构如何衔接。

不得为写后续小节而跳过当前小节的未决问题。确实需要后续机制才能解释时，明确建立交叉引用并限定当前结论，不提前展开后续章节。

### 4. 整理为书稿内容

每个章节使用连贯的教学叙事，而不是源码检索日志。章节至少包含：导言与学习目标、前置知识、分层小节、必要的 Mermaid 图、关键源码证据、章节总结、与其他章节的关系，以及尚未解决的问题。

每个小节先解释源码能够确认的概念和问题，再描述代码如何实现，最后按“关键源码呈现规范”给出最小源码节选或逻辑缩减及精确证据。优先用自己的语言解释已验证的不变量和执行过程。图示必须服务于当前小节，并与经过源码验证的能力架构保持一致。

### 5. 章节门禁

完成当前章节后，逐项审计关键结论和图示关系是否都有具体源码证据，检查该章所有小节是否都有明确问题、实现解释和源码位置，并核对其与能力架构图、前置章节及覆盖矩阵是否一致。发现无证据结论时删除或移入“尚未确认的问题”。先输出或写入完整章节内容，再标记该章完成；未通过检查时不得进入下一章。

若精读证据推翻了第二阶段的推断，应明确记录修正原因并更新能力架构及后续章节计划，不能悄悄改写旧结论。修正不允许跳过当前章节或重排已确认目录；确需调整目录时先向用户说明并重新确认。

### 第三阶段完成条件

阶段记录必须包含：经确认的全书目录、能力覆盖矩阵、按顺序完成的全部章节及小节、跨章节术语与源码索引、对第二阶段能力架构的验证或修正记录、章节证据审计结果，以及全书遗留问题清单。任一大能力只有章节标题而没有小节内容，正文退化为按文件逐个说明，或存在无法追溯到源码的关键结论时，第三阶段不算完成。

## 第四阶段：Markdown 落盘与逐章复核

目标是在第三阶段完整书稿的基础上生成标准 Markdown 产物，再按照 Markdown 章节逐章回到固定 commit 核对源码逻辑，确保文档中的每个关键知识点都对应到具体源码。

开始前确认第三阶段已达到全部完成条件，并再次校验 tag 仍解析到记录中的同一 commit SHA。若 tag 已移动，以第三阶段记录的 commit SHA 为证据锚点并明确报告差异；不得混用新旧版本。

### 1. 建立版本化产物目录

产物根目录固定为当前工作目录下的 `.read-source/`。使用源码仓库名建立下一级目录，再使用文件系统安全的 tag 名隔离不同版本：

```text
.read-source/
`-- <源码仓库名>/
    `-- <tag>/
        |-- README.md
        |-- chapters/
        |   |-- 01-<章节名>.md
        |   `-- 02-<章节名>.md
        |-- source-index.md
        `-- verification.md
```

仓库名取源码仓库根目录名；若目录名不能唯一识别仓库，则使用远程仓库名并记录来源。tag 含 `/`、空格或其他不安全字符时，仅对目录名进行可逆或明确记录的安全化处理，Markdown 内仍保留原始 tag。

写入前检查目标目录。若同一仓库和 tag 的产物已存在，只更新本次书稿对应的文件并保留无关内容；若发现版本元数据不一致或无法识别的同名文件，先报告冲突并请求用户确认，不得直接覆盖。

### 2. 生成标准 Markdown 书稿

`README.md` 作为全书入口，包含仓库标识、原始 tag、完整 commit SHA、版本校验结果、项目简介、目录和阅读顺序。`chapters/` 中每个经确认章节对应一个 Markdown 文件，小节保留第三阶段确定的稳定编号。`source-index.md` 汇总知识点与源码证据，`verification.md` 记录逐章核对结果和修订。

所有文件使用 UTF-8、标准 Markdown 标题、列表、表格、带语言标识的代码围栏和标准相对链接。每个章节文件只使用一个一级标题；Mermaid 图使用 `mermaid` 围栏。不要依赖只在特定编辑器中生效的私有指令。

每个章节开头重复标注原始 tag 与完整 commit SHA。源码引用必须包含仓库相对路径、符号名和精确行号；能生成指向该 commit 的稳定远程链接时同时提供，不能时保留可持久定位的文本引用，不能链接到可能变化的当前分支。

### 3. 建立关键知识点证据索引

为每章的关键知识点分配稳定编号。关键知识点包括公开契约、核心数据结构与不变量、控制流、数据流、状态转换、重要分支、错误处理和扩展边界。

在正文相关段落附近标注知识点编号和源码引用，并在 `source-index.md` 中记录：知识点编号、简明结论、所属章节与小节、源码路径、符号、行号、正文中的源码呈现方式、交叉验证证据和核对状态。一个知识点涉及多个组件时列出完整证据链，不能只引用入口文件。

### 4. 按 Markdown 章节逐章核对

严格按照 `README.md` 目录顺序，一次只核对一个章节。核对时重新读取固定 commit 的源码，不把第三阶段笔记本身当作证据。逐项检查：

- 每个关键知识点是否与实际定义、调用路径和测试一致；
- 描述的控制流、数据流、状态变化、分支条件和错误路径是否完整准确；
- 代码片段、符号名、路径和行号是否对应当前 commit；
- 源码节选是否保持原始语句，逻辑缩减是否保持原始符号、条件、顺序、副作用及返回/错误语义；
- 每个关键逻辑是否展示了足够理解的最小源码，而没有复制无关的大段实现；
- Mermaid 图中的重要节点和连线是否都有源码支撑；
- 章节之间的术语、前置关系和交叉引用是否一致。

核对结果只能是“已验证”“已修正”或“未获源码支持”。发现错误时，以源码为准修正文档、图示和证据索引，再重新核对该知识点；未获支持的内容从正文和图示中删除并移入遗留问题。当前章节仍有未核对的关键知识点时，不得进入下一章。

在 `verification.md` 中按章节记录核对范围、证据、发现的问题、修改内容和最终状态。不能只写笼统的“已检查”。

### 5. 全书一致性审计

所有章节核对完成后，检查目录链接、章节编号、标题层级、代码围栏、Mermaid 围栏、术语、交叉引用、知识点编号和源码索引是否一致。确认正文中没有指向其他 tag、当前分支或未经验证源码的结论。

最终在 `verification.md` 汇总已验证、已修正和被移除的知识点数量，并记录全书使用的仓库、tag、完整 commit SHA、核对完成状态及仍存在的源码边界。任何正文关键知识点缺少源码对应关系时，第四阶段不得完成。

### 第四阶段完成条件

版本化目录及规定的 Markdown 文件全部存在；每章均通过逐章核对；正文、代码片段、逻辑缩减和图示中的关键知识点都能在 `source-index.md` 找到对应源码；关键逻辑包含最小且可识别的源码呈现；`verification.md` 留有具体核对记录和全书汇总；正文不包含“未获源码支持”的结论，也没有无必要的大段源码复制。缺少任一条件时，不得宣布产物完成。

## 控制范围

- 第一阶段只做宏观认知，即使发现明显入口，也只把它记入后续问题清单，不继续追踪。
- 第二阶段只形成有源码证据的能力级模型，不穷举所有实现分支，也不把推断包装成事实。
- 第三阶段严格按确认后的目录逐章逐节精读；未完成当前章节时，不得切换到下一章。
- 第四阶段只把第三阶段已经完成的书稿落盘并按章复核，不能借落盘之名添加未经精读的新结论。
- 遇到生成代码、第三方依赖或运行时注入时，标明边界，不假装已看到外部实现。
- 只有当用户询问“为什么这样写”或历史原因时，才使用 Git 历史或 blame；不要用历史替代当前实现证据。
- 用户只要求阅读、解释或诊断时，不修改源码仓库。第四阶段仅可在当前工作目录的 `.read-source/` 中创建或更新约定的 Markdown 产物；若同时要求实现源码变更，先完成必要的源码理解，再在既定范围内修改。

## 输出要求

先给出版本锚点，再给出当前阶段的记录。引用该 commit 中的真实文件及尽可能精确的行号；只有链接确实指向所分析版本时，才使用可点击的本地绝对路径链接。清楚区分：

- 当前阶段证据可直接确认的事实；
- 根据多处证据得出的推断；
- 因缺少运行时状态、外部依赖或配置而仍不确定的部分。

避免逐文件复述、粘贴大段内容或只列名称。解释每项关键证据为何相关，以及它在当前阶段认知模型中的作用。

第三阶段的输出使用稳定的“章 → 节 → 小节内容”层级，保持术语、编号和交叉引用一致，使各章合起来能够作为连续阅读的源码书稿。

第三阶段正文只容纳源码已验证的内容。仍需验证的假设只能进入独立的“尚未确认的问题”区，不得参与正文推导或图示建模。

第四阶段完成时，最终回复必须给出产物目录、仓库、tag、完整 commit SHA、章节核对状态和遗留边界；不能只说“文档已生成”。
