# Read Source 完整工作流

以用户的问题为中心阅读源码。先判断项目类型，再按类型选择精读入口，最后只沿核心能力追实现；不要为了“了解整个仓库”而无边界地遍历文件。

## 源码范围

- 默认阅读当前工作区源码。
- 用户指定版本、tag 或 commit 时，先固定该快照，后续只从该快照读取文件和搜索符号。优先直接读取 Git 对象；确需普通文件树时使用隔离的临时 worktree，不要改动用户当前 checkout。
- 未指定版本时，不要自行切换分支或 checkout tag。
- 证据来自外部依赖或其他仓库时，明确标注边界，不能混入当前仓库结论。

## 产物目录

开始前先确定本次任务唯一的产物项目目录名：

1. 新任务默认使用源码仓库名作为 `<项目名>`，目标为 `.read-source/<项目名>/`。
2. 若该目录已经存在，使用任务开始当天的本地日期追加 `_YYYY-MM-DD`。
3. 若同一天的带日期目录也已存在，继续追加递增序号，直到取得不存在的目录；不得覆盖其他任务的目录。
4. 若是在恢复未完成任务，读取其 `manifest.md` 并继续使用已记录目录。

在当前工作目录建立：

```text
.read-source/
`-- <产物项目目录名>/
    `-- temp/
        |-- manifest.md
        |-- 01-project-type.md
        |-- 02-capability-map.md
        `-- 03-architecture.md
```

`manifest.md` 记录源码仓库名、产物目录、各步骤状态及产物清单；每完成一步立即更新。对话回复只是摘要，完整结果必须落到对应 Markdown。产物未写入并检查可读性时，该步骤不算完成。

任务中断或校验失败时保留整个 `temp`。只有第三步最终产物完整通过检查后，才删除该 `temp` 目录。

## 步骤纪律

- 不得跳过、合并、调换或并行执行步骤，也不得因用户问题看似具体就直接进入实现细节。
- 当前步骤的必读范围、产出和完成条件全部满足后，才能进入下一步。
- 每完成一步，先写入约定产物并检查；通过后更新 `manifest.md`，给出简短进度与产物路径，并立即进入下一步，不询问、不等待用户确认。
- 检查失败时留在当前步骤修正。只有缺少访问权限或存在不允许覆盖的未知文件等无法自行解决的阻塞，才停止并保留 `temp`。

## 第一步：定位项目类型

目标是回答“这是什么类型的项目、解决什么问题、后续应沿哪类入口精读”，而不是开始读实现。

### 1. 读文档

阅读仓库中实际存在的说明文档，按此优先顺序，存在则读，不存在则跳过并记录缺失：

1. `README` / `README.md`
2. `AGENTS.md`、`CLAUDE.md`、`CONTRIBUTING.md` 等给代理或贡献者的说明
3. `docs/`、`documentation/`、官方架构说明
4. 示例目录的说明，例如 `examples/`、`playground/` 中的 README

提取并记录：

- 项目要解决的核心痛点，以及目标用户为何需要它
- 项目能力边界、主要适用场景与明确不适用的场景
- 项目自创或赋予特殊含义的核心术语
- 文档暂未回答、需要后续步骤验证的问题

本步骤只建立官方叙事。文档没有说明的内容标为未知，不自行补全，也不进入具体源码验证。

### 2. 看清单与技术栈

检查仓库实际存在的依赖与构建清单，例如 `package.json`、`go.mod`、`Cargo.toml`、`pyproject.toml`、`requirements.txt`、工作区清单及锁文件。识别：

- 主要语言、运行时、框架和关键库
- 包导出、二进制入口、工作区包划分
- 构建、测试、打包方式
- 从清单能直接确认的对外形态：库导出、CLI bin、脚手架模板、Agent 配置等

依赖文件能直接确认的内容记为事实；对项目类型的判断若还需文档或目录佐证，标为待确认。

### 3. 判定项目类型

综合文档、清单和一级/二级目录（不展开更深，也不读业务实现），判定**主类型**；若同时具备多种形态，再记录次要类型。主类型从以下选取，不能用目录名直接代替类型：

| 主类型 | 典型信号 |
| --- | --- |
| 工具库 | 以导出函数、类或模块为主；README 强调 API；`package.json` 有 `exports`/`main`，通常无 UI 组件目录 |
| UI 库 | 以组件、样式、主题或无头原语为主；文档按组件组织；存在 `components/`、stories 或 playground |
| CLI 工具 | 有 `bin`、cobra/click/commander 等命令定义；README 以命令和 flags 说明用法 |
| 脚手架 | 用于生成项目、页面、组件或配置；存在 `templates/`、generator、preset 或 create-* 入口 |
| Agent 项目 | 以 agent、skill、tool、prompt、runtime loop 为核心；存在 `SKILL.md`、tools 注册或 agent 配置 |
| 应用或框架 | 以上都不贴切时使用；例如完整应用、开发框架、运行时。写明它更接近哪一类，以及为什么 |

判定时写出依据与置信度。信号冲突时列出冲突，选最能代表**使用者主要用法**的主类型，不要为了齐全同时当作多个主类型。

第一步结束时必须明确：后续第二步应采用哪份类型策略。混合项目只选一份主策略，次要类型仅作为补充入口。

### 第一步完成条件

将记录写入 `temp/01-project-type.md`。必须包含：一句话定位、主类型与次要类型、判定依据、核心痛点、适用场景、核心术语表、技术栈概览、文档与清单中的对外入口线索、留给后续步骤的问题清单。缺少主类型或判定依据时，第一步尚未完成。

## 第二步：按类型摸清核心能力

目标是回答“对使用者来说，这套代码提供哪些核心方法、组件、命令或生成能力”。这里建立的是**对外能力清单**，不是仓库目录图，也不是完整架构。

开始前读取第一步记录。主类型缺失或不完整时返回第一步。随后阅读 [项目类型精读策略](project-types.md) 中对应主类型章节，按其入口执行，不要套用其他类型的读法。

### 1. 选择精读入口

按主类型选择表面入口，而不是从 `src/` 第一层文件顺读：

- 工具库、UI 库：公开导出、README API、组件文档、类型声明
- CLI 工具：命令定义、`--help`、bin 入口
- 脚手架：生成器入口、模板目录、preset/plugin 清单
- Agent 项目：agent 定义、skill/tool 清单、系统提示或 loop 入口
- 应用或框架：用户主路径对应的公开入口，例如路由、插件或生命周期钩子

只读能帮助列出核心能力的入口、导出、示例和关键测试。不要在本步穷举分支或逐行钻研实现。

### 2. 建立核心能力清单

从使用者视角列出核心能力。不要把目录名、包名或内部类名直接当作能力。

为每项能力记录：

- 对外名称：函数、组件、命令、生成器、skill 或 tool 的原始符号
- 使用者如何触发它
- 输入、输出和可见副作用
- 它解决什么问题
- 定位到的入口文件与符号

能力应按使用时的分组整理，例如工具库按方法族、UI 库按组件族、CLI 按命令树。先抓主干，不把所有工具函数或实验性导出都列入核心。

### 3. 标出深入线索

为第三步标出最值得追入的线索，而不是现在追完：

- 哪些能力共享同一套内核、调度、渲染、生成或 loop
- 哪些入口最能带出架构主路径
- 哪些问题文档未说明，必须用实现回答

### 第二步完成条件

将记录写入 `temp/02-capability-map.md`。必须包含：主类型与所采用的精读策略、核心能力清单、能力分组、入口符号与文件、准备带入第三步的主路径线索，以及尚未验证的问题。清单若只是目录罗列，或未出现原始对外符号，第二步不算完成。

## 第三步：结合核心能力深入架构

目标是顺着第二步的核心能力进入源码，回答“这些能力在运行时如何协作、内部架构是什么”，并把学习结果写成可复核的笔记。

开始前读取第一、第二步完整记录，确认能力清单和主路径线索已经完成。任一条件不满足时返回对应步骤。

### 精读证据纪律

- 函数名、类型名、目录名、注释和搜索命中只能作为定位线索，不能代替实现证据。必须阅读完整定义、关键调用方及必要上下文。
- 前两步标为“推断”的内容进入第三步后只是假设，必须重新用源码验证。验证前不得写入架构结论。
- 关于控制流、数据流、状态转换、边界条件和错误处理的每个关键结论，都必须能追溯到具体符号与源码位置。
- 不得因为项目使用常见框架，就假设它遵循该框架的典型实现。只描述实际读取的源码行为。
- 源码能证明“如何工作”，未必能证明“为什么这样设计”。没有注释、文档或用户指定的历史依据时，写成可观察的作用，或标为尚未确认。
- 证据不足的内容放入“尚未确认的问题”，不能用“大概”“通常”“应该”包装进正文。

### 关键源码呈现

- 保留原始类名、方法名、函数名、类型名和关键字段名。
- 只给出理解当前知识点所需的最小“源码节选（有删减）”；删除无关样板时用明确省略标记。
- 需要进一步压缩时，另给“逻辑缩减（非原始源码）”，并保留原始符号、条件、顺序、副作用和返回语义。
- 每段节选紧邻标注仓库相对路径、原始符号和行号。不得大段复制整文件。

### 1. 沿核心能力追实现

按第二步标出的主路径，从对外符号追到核心实现和出口。阅读完整的相关函数、类型及必要上下文，并用定义、调用方、测试和错误路径交叉验证。

重点确认：

- 这项能力实际由哪些运行时角色共同完成
- 控制如何进入、转移并结束
- 关键数据如何产生、转换和传递
- 是否存在调度、缓存、并发、事件、插件、模板渲染或宿主环境等协作边界
- 正常路径、关键分支和失败路径如何处理

一次沿一条主路径深入。不要抛开能力清单改按文件树阅读。若精读推翻了前两步的类型或能力判断，明确记录修正原因，并更新对应产物后再继续。

### 2. 抽象架构

从已验证的主路径抽象架构，而不是把目录画成架构图：

- 组件按运行时职责命名，目录和文件只作证据索引
- 区分对外能力、核心机制、基础支撑与外部边界
- 标出控制流、数据流、事件流或依赖方向
- 无法确认的关系标为推断，不能画成已证实事实

使用 Mermaid 绘制必要图示：必须有一张总体架构图；对最有代表性的端到端场景补时序图；只有真实存在生命周期或状态机时才画状态图。

### 3. 整理学习笔记并落盘

最终产物直接写入 `.read-source/<产物项目目录名>/`：

```text
.read-source/
`-- <产物项目目录名>/
    |-- README.md
    |-- capability-map.md
    |-- architecture.md
    `-- source-index.md
```

- `README.md`：项目类型、一句话定位、推荐阅读顺序、核心能力总览
- `capability-map.md`：第二步核实后的对外能力清单与入口
- `architecture.md`：由浅入深的架构说明；按能力主路径组织，不按文件平铺；必要时拆成同目录 `architecture/` 下的分篇
- `source-index.md`：关键知识点到源码路径、符号、行号的索引

正文使用连贯叙述：先回顾类型与核心能力，再沿主路径讲清架构，最后列出尚未确认的问题。每个关键知识点都必须能映射到源码位置。

写入前检查目标目录；发现无法识别的同名文件时先报告冲突，不得直接覆盖。最终目录完整通过检查后，只删除本次任务的 `temp/` 精确目录，不删除最终 Markdown。

### 第三步完成条件

最终目录及规定文件全部存在；主类型和核心能力已反映到 README 与能力清单；架构说明沿核心能力展开且关键结论都有源码证据；`source-index.md` 能从知识点回到路径、符号和行号；正文不含无证据结论，也没有无必要的大段源码复制；`temp` 已按精确路径删除且最终目录仍可读。缺少任一条件时，不得宣布完成。

## 控制范围

- 第一步只定位类型和官方叙事，即使发现明显入口，也只记入后续线索，不继续追踪实现。
- 第二步只建立对外核心能力清单，不穷举所有实现分支。
- 第三步只沿已确认的核心能力深入；未完成当前主路径时，不得改去平铺阅读其他目录。
- 遇到生成代码、第三方依赖或运行时注入时，标明边界，不假装已看到外部实现。
- 只有当用户询问“为什么这样写”或历史原因时，才使用 Git 历史；不要用历史替代当前实现证据。
- 用户只要求阅读、解释或诊断时，不修改源码仓库。第三步仅可在 `.read-source/` 中创建或更新约定产物。

## 输出要求

直接给出当前步骤摘要和产物路径。引用实际读取的真实文件及尽可能精确的行号。清楚区分：

- 当前步骤证据可直接确认的事实
- 根据多处证据得出的推断
- 因缺少运行时状态、外部依赖或配置而仍不确定的部分

避免逐文件复述。解释每项关键证据为何相关，以及它如何服务当前步骤的认知目标。

第三步完成时，最终回复必须给出最终产物目录、项目类型、核心能力概要、架构结论和遗留边界；不能只说“文档已生成”。
